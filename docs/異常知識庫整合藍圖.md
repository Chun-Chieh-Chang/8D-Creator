# 個人異常管理知識庫整合藍圖

日常操作可使用 [8D Creator 案件工作區](./案件工作區.md)。下方流程也適用於直接使用 Obsidian 或命令列的情境。

## 使用流程

1. 在 Obsidian 選取「開啟資料夾作為儲存庫」。
2. 選取本機設定中的知識庫資料夾。
3. 從「首頁」開啟案件或缺陷索引。
4. 在案件的「複核筆記」查閱來源附件。
5. 在 8D Creator 產生 8D 報告，或從「歷史報告」開啟一份報告。
6. 選取「匯出 Obsidian 草稿 JSON」。
7. 用下方 `attach` 命令將草稿連到案件 ID。
8. 依原始證據更新複核屬性。
9. 執行 `sync` 更新索引。

複核 D2 的問題描述、D3 的臨時遏制措施、D4 的發生與流出原因、D5 和 D6 的措施，以及 D7 的措施驗證。將已驗證的措施、適用條件和再發判定寫入複核筆記。補件時，將附件存入對應的來源資料夾，再執行 `sync`。

## 架構與推進

| 階段 | 實作 | 驗收 |
|---|---|---|
| 1．歷史盤點 | 日期開頭的案件資料夾，以及廠內 CAPA 活頁簿的案件列。其他檔案及無法解析的列進缺口頁。資料夾日期採來源標示，CAPA 日期是發出日期 | 掃描數可對帳。案件可回到來源資料夾或工作表列。原始資料零寫入 |
| 2．複核與 8D | Obsidian 複核筆記及受控缺陷詞彙。匯出草稿 JSON 後，可用 CLI 匯入至指定案件並保存獨立草稿版本 | 空白及格式錯誤報告拒收。相同案件及內容重送只留一份。草稿不改複核狀態 |
| 3．成長與檢索 | 缺陷詞彙索引、待補證據、待查重、來源失聯。以人工核准結果回饋分類 | 重跑無變動。增量加入新案後 ID 保持穩定。來源失聯保留複核與草稿；重複案保留兩條來源 |
| 4．Auto Ontology | 明確執行本機 PostgreSQL 匯出，投影有證據的案件、受控概念與關係。部署後將投影接到 NVIDIA 語義目錄，編譯及複核定義，經唯讀 MCP 查詢 | 先驗 SQL 與欄位邊界，再用測試資料驗語義編譯、問題可回答性、SQL、筆數和溯源。通過後才接經核准資料 |

## 資料與知識治理

- 案件 ID 由來源類型與相對定位決定。CAPA 用編號＋發出日期，資料夾用相對路徑。來源位置異動先跑同步查看失聯，再透過儲存庫的 `source-aliases.json` 把新資料夾的相對路徑（以 `/` 分隔）映射到舊案件 ID，然後重跑。若已同步出新 ID，先保留兩份複核並用 `duplicate_of` 指向主案。
- 案件頁的品號字串及缺陷是來源標題或摘要比對出的線索。跨案件共用編號也只列為候選。人工在複核筆記填寫 `defect` 與 `evidence_path`、`evidence_locator`、`finding`，才可把狀態改成 `reviewed`。證據用來源根目錄下的相對路徑，定位寫頁碼、列號或圖號。結案另需 `verification_path`、`verification_locator`、`verification_result`，結果記錄驗證期間、樣本數、判定標準與實測結果。
- 每次新增資料後同步，先處理失聯與缺口，再複核高重複、高影響案件。每月以缺陷索引回顧已複核案件。新增同義詞時修改 `詞彙表.yml`，保留既有 concept ID，重跑後核對索引及複核值。新增概念時給它獨立 ID 與定義，並以真實例與反例核對命中情形。
- 來源及複核筆記留在本機。同步器維護案件索引、詞彙索引、草稿索引及缺口頁。人工內容放在複核筆記。定期備份整個儲存庫，包含隱藏的 `.quality-kb` 索引資料。
- 附件目前用檔名與路徑索引。PDF、圖片、郵件及歷史表單的內容仍待逐案複核。日期代表來源的標記；要分析實際發生時間，先另行核實。沒有出貨量或生產批數分母時，只能算案件數。

## 執行方式

在 8D Creator 專案目錄執行。路徑由本機 config.json 設定。可用 `--source` 與 `--vault` 改到測試目錄。

```powershell
npm run kb -- sync
npm run kb -- attach <案件ID> 'C:\path\8D-kb-報告.json'
npm run kb -- verify
npm run kb -- export-sql 'C:\path\quality-kb.sql'
```

- `sync` 掃描及重建索引。修正複核屬性後重跑。
- `verify` 唯讀重算索引，檢查過期輸出、無效複核、草稿指紋和來源碰撞。歷史缺件及可能重複會列出待辦。
- `attach` 將草稿固定到選定案件。先同步、在 Obsidian 核對來源，複製案件 ID 再匯入。相同快照可重送。
- `export-sql` 產出可用 `psql -v ON_ERROR_STOP=1 -f <檔案>` 匯入的交易。每次重建專用 `quality_kb` schema 下的三張資料表內容。匯出時指定新的檔名。資料集只含經複核且來源可用的主案 ID、年份、來源類別、複核狀態及受控缺陷概念與同義詞。產品、公司名稱、附件位置及報告全文保留在 Obsidian。

## NVIDIA Auto Ontology 接入與驗證

上游基準 [fc43a826](https://github.com/NVIDIA/auto-ontology/tree/fc43a82600e18b19d159c52023f54f5572f537ac)。依該版官方 Quickstart 起本機 Compose 與模型服務。將 `quality_kb` 匯入專用資料庫，給查詢角色 schema USAGE 和三張表的 SELECT。將該庫的唯讀連線加入 `CONNECTION_STRINGS`，在 Settings 啟動 Semantic Compilation。目錄中核准案件、缺陷及對應關係的定義和基數。之後可用上游模型匯出保存定義，並用 MCP 的 `check_readiness`、`search_terms`、`check_answerable` 和 `ask_question` 驗證。

| 驗證題 | 判準 |
|---|---|
| 供應商異常中，各年度已複核的色差有幾案？ | 與 SQL 基準的 `COUNT(DISTINCT case_id)` 一致，年度是來源日期年份，可從 ID 回查本機證據 |
| 未核實的「缺料」線索是否進入彙總？ | 0 筆。被合併、失聯及待複核案同樣排除 |
| 同一缺陷的中文同義詞能否得到相同查詢？ | 至少一對同義詞返回相同案件集合，人工核對 SQL 篩選和關聯 |
| 不良率、根因或措施成功率是多少？ | 語義層應辨識缺少對應資料並要求補充 |
| 匯入新案或確認重複後，結果是否更新？ | 重新匯出並匯入，再次查詢，結果與本機基準一致 |

模型服務、資料庫與 MCP 部署需另行驗收。可先用下方合成案例驗證投影，避免以真實案件測試模型連線。

```powershell
node --test scripts/quality-kb/kb.test.mjs
npx tsc --noEmit
```
